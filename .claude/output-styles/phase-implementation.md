# 出力スタイル: 実装フェーズ

このスタイルは `/implementing-features`, `/refactoring` skill 実行時、コードを書く全シーンで使用する。
**書く前に必ずテスト**、書いた後に必ず検証する。

## 振る舞いの原則

1. **Red-Green-Refactor** — 失敗するテスト → 通すコード → リファクタの順を厳守
2. **最小差分** — 1コミット1責務。無関係な改善を混ぜない
3. **検証ファースト** — 実装後は必ずテスト実行・型チェック・lint を行いログを示す
4. **既存パターン尊重** — Glob/Grep で類似実装を確認し、パターンに合わせる
5. **dry-run 思考** — 変更を加える前に「何が起きるか」を1〜2行で予告
6. **依存方向違反ゼロ** — `project-config.md` §4.4 の依存ルールを侵さない
7. **ドキュメント同期** — 実装変更に伴い `docs/` を更新する

## 出力形式

- コード変更は短いセクションに分割し、各々で「目的→差分→検証」の3段で報告
- テスト結果は pass/fail 件数とログを必ず示す
- カバレッジ・lint・型エラー数の前後比較を出す
- 未解決の TODO は明示的にコメント or 後続タスクへ

> **N/A の許容**: テスト基盤・カバレッジ計測・型チェック・lint のいずれかが
> プロジェクトに未導入(or `project-config.md` で未有効化)の場合、
> その項目は **「未実施(N/A)+ 理由 + 次アクション」** の形で報告してよい。
> 例: 「カバレッジ: N/A(vitest 未導入、§6 で coverage 目標未設定)。次: §6 設定後に有効化」。
> 虚偽の数値を報告しないことが最優先。

## 禁止事項

- `--no-verify` の使用
- 失敗したテストの skip / 削除による「緑化」
- デバッグコードの残存(言語別: JS の `console.log`、Python の `print` / `logger.debug`、
  Go の `fmt.Println`、Rust の `dbg!` / `println!`、Ruby の `puts` / `pp`、Swift の `print`)
- フックを迂回した強行コミット
- 推測でのフィールド追加・削除

## 想定されるフォローアップ

- 実装完了後 `/code-review` で自己レビュー
- E2E カバレッジが必要なら `/e2e-testing` を呼ぶ
- パフォーマンス影響があれば `/performance`
