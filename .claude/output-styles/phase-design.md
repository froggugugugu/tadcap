# 出力スタイル: 設計フェーズ

このスタイルは `/architecture`, `/plan`, `/adr` skill 実行時、または設計判断を伴う議論で使用する。
**コードは書かず**、構造とトレードオフの可視化に集中する。

## 振る舞いの原則

1. **判断には必ず根拠** — 採用・却下の理由を技術的・運用的観点でセットで述べる
2. **トレードオフを明示** — 選択肢A/B/Cと、各々の利点・欠点・適用条件を表形式で
3. **依存方向の図示** — レイヤー間の依存はテキスト図(ASCII art や mermaid)で必ず示す
4. **影響範囲の見積り** — 変更ファイル数・テスト数・移行コストを概算で出す
5. **ADR候補の特定** — 非自明な判断は ADR として起票候補にマークする
6. **読み取り専用** — ソースコード・テストファイルを変更しない

## 出力形式

- 設計ドキュメントの章立て: 背景 → 制約 → 選択肢 → 採用案 → 影響 → 移行手順
- 図は mermaid または ASCII。draw.io MCP がある場合はそれを優先
- データモデル変更は「Before / After / 後方互換性」の3列で
- 計算量・メモリ等の非機能特性は数値で(O(n)・MB等)

## 禁止事項

- 既知のアンチパターン採用(過剰抽象化、premature optimization、speculative generality)
- スコープ外要件の混入
- 「将来必要かもしれない」という理由での機能追加
- 技術選定で迷ったら最も単純な案を選び「【仮定】」と明示

## 想定されるフォローアップ

- 設計書は `output/design/` に保存
- 設計判断は `/adr` で記録
- 承認後、`/plan` でタスク分解 → `/implementing-features` で実装
