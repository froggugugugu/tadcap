# ワークフロー制御 — 自己改善・検証・自律性

> **path-specific rule**: 実装対象のソースツリーに触れたときだけ自動 load される

> CLAUDE.md 肥大化防止のため切り出したルール。上の frontmatter に従って自動 load され、必要な skill からは `@import` でも明示参照できる。
> 計画ファースト / サブエージェント戦略は CLAUDE.md 本体、調査ファーストは AGENTS.md の開発原則に残し、
> ここは "自己改善ループ以降" の高度なワークフロー指針を集約する。

## 1. 自己改善ループ

- ユーザーから修正を受けたら、`.claude/tasks/LESSONS_TEMPLATE.md` の形式で学びを記録する
- 同じミスを繰り返さないルールを自分で書く
- ミス率が下がるまで学びを反復的に改善する
- セッション開始時に関連プロジェクトの学びを確認する
- 成功パターンは `.claude/learnings/` に confidence スコア付きで蓄積する(`pitfalls.md` の対概念)

## 2. 完了前の検証

- 動作を証明せずにタスクを完了にしない
- 必要に応じて main ブランチとの差分を比較する
- 「シニアエンジニアがこれを承認するか?」と自問する
- テスト実行・ログ確認・正しさの実証を行う
- UI 変更は Playwright MCP でのビジュアル確認を含める
- **証拠を示す**: 「動くはず」ではなく、テスト出力・実行コマンドと戻り値・スクリーンショットを貼る。
  検証手段が無ければ先に作る(テスト / スクリプト / fixture との diff / `/verify` での実アプリ確認)
- レビュー subagent には「正確性と要件に影響する gap のみ報告」と指示する。
  指摘を出すこと自体が目的化したレビューを全件対応すると過剰設計になる

## 3. エレガンスの追求(バランス型)

- 非自明な変更では「もっとエレガントな方法はないか?」と立ち止まる
- ハック的な修正に感じたら「すべてを知った上で、エレガントな解決策を実装する」
- 単純で明白な修正にはこれを適用しない — 過剰設計を避ける
- 提出前に自分の成果物を批判的にレビューする

## 4. 自律バグ修正

- バグ報告を受けたら、手取り足取りの指示を求めず自力で修正する
- ログ・エラー・失敗テストを特定し、解決する
- ユーザーのコンテキストスイッチをゼロにする
- CI 失敗も指示を待たず自律的に修正する

## 5. タスク管理(2 形式)

| 手段 | 用途 | 永続性 |
| ---- | ---- | ------ |
| `TaskCreate` / `TaskUpdate` | セッション内の作業進捗追跡 | セッション限り |
| `.claude/tasks/` テンプレート | チーム間で共有するタスク仕様書 | ファイルとして永続 |

### セッション内の進捗管理

1. 計画を立てる: `TaskCreate` でチェック可能な項目を作成
2. 計画を確認する: 実装開始前にチェックインする
3. 進捗を追跡する: 完了した項目を `TaskUpdate` で随時マーク
4. 変更を説明する: 各ステップでハイレベルなサマリーを提示

### 永続的なタスク仕様書

1. 結果を記録する: 完了時にレビューセクションを追加
2. 学びを蓄積する: 修正を受けたら `.claude/tasks/LESSONS_TEMPLATE.md` の形式で記録

## 6. 長期タスクの引き継ぎ(複数コンテキストウィンドウ)

Anthropic の長時間エージェント運用知見(initializer / coding agent パターン)に基づく。
1 セッションで一気に作らず、**次のセッションが推測なしで再開できる状態**で終える。

| 失敗パターン | 対策 |
| ------------ | ---- |
| 一気に作ろうとして途中でコンテキストが尽きる | **1 セッション 1 機能**。`output/tasks/PROGRESS.md` の機能リストから最優先の未完了 1 件だけ選ぶ |
| 途中の状態が未記録で次セッションが推測から始まる | 終了前に **コミット + PROGRESS.md 更新**(やったこと / 検証結果 / 次の一手 / 却下した案) |
| 進捗を見て「完成」と早合点する | 機能リストの `passes` は **検証して初めて ✅**。行の削除・受け入れ条件の書き換えは禁止 |
| 起動方法を毎回探し直す | 起動 → スモークテストの手順を PROGRESS.md に固定し、セッション冒頭で実行して壊れていないことを確かめてから着手 |

セッション開始の定型: `pwd` → `git log --oneline -10` → PROGRESS.md → スモークテスト → 1 機能着手。
雛形は `.claude/tasks/PROGRESS_TEMPLATE.md`。SessionStart フックが PROGRESS.md の冒頭を自動注入する。
会話内で完了条件まで自走させたいときは `/goal <条件>`、セッションをまたぐ定期実行は GitHub Actions に置く。

## 基本原則

- **シンプルさ優先**: すべての変更を可能な限りシンプルに。影響範囲を最小限に
- **妥協しない**: 根本原因を特定する。一時的な修正は行わない。シニア基準で判断
- **影響を最小化**: 変更は必要な箇所のみに留める。バグを持ち込まない
