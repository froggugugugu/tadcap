### HIGH(1週間以内)

- [ ] **[HIGH]** `src-tauri/src/commands.rs:333-346`(`parse_image_dimensions`)/ `src-tauri/src/clipboard/mod.rs:44-60`(`validate_rgba`) `write_image_fallback` の width/height 整数オーバーフローによる長さ検証バイパス。
  **CVE/CWE**: CWE-190(Integer Overflow or Wraparound)/ CWE-20(Improper Input Validation)。関連で下流に CWE-125(Out-of-bounds Read)の可能性(未確認、下記参照)。
  **影響**: `write_image_fallback` は `IMAGE_WIDTH_HEADER`/`IMAGE_HEIGHT_HEADER`(文字列ヘッダー)を `usize` にパースするのみで上限チェックが無い(`commands.rs:333-346`)。`validate_rgba` は `width * height * 4` をチェックなしの通常乗算で計算する(`clipboard/mod.rs:52`)。
  `src-tauri/Cargo.toml:32-37` の `[profile.release]` は `panic = "abort"` を明示するが `overflow-checks` は指定していないため、Cargo公式ドキュメント(`https://doc.rust-lang.org/cargo/reference/profiles.html#release`)の既定どおり **release ビルドでは `overflow-checks = false`(オーバーフロー時に無言でラップアラウンドする)** になる。
  具体的な攻撃シナリオ(64bit `usize` 前提、macOS標準):
  `invoke("write_image_fallback", <空のRawボディ>, {headers: {"x-tadcap-image-width": "4294967296", "x-tadcap-image-height": "4294967296"}})` を呼ぶと、
  1. `parse_image_dimensions` は `width=4294967296, height=4294967296` を正常な `usize` として受理する(上限チェックが無いため)。
  2. `validate_rgba` の `width == 0 || height == 0` チェックは通過する(いずれも非ゼロ)。
  3. `expected = width * height * 4` は `4294967296 * 4294967296 = 2^64 ≡ 0 (mod 2^64)`、`0 * 4 = 0` となり `expected = 0` にラップアラウンドする。
  4. 空のボディ(`bytes.len() == 0`)を送ると `bytes.len() != expected`(`0 != 0`)が成立せず**検証を通過**し、`clipboard::write_image_fallback(4294967296, 4294967296, [])` が呼ばれ、`arboard::ImageData { width: 4294967296, height: 4294967296, bytes: Cow::from(vec![]) }` が `Clipboard::set_image`(macOSネイティブのクリップボードAPIへのFFI境界)へそのまま渡る(`clipboard/mod.rs:68-82`)。
  この経路より先(`arboard` 内部・CoreGraphics/AppKitブリッジ)が実際に宣言サイズ通りにバッファを読み取ろうとした場合のクラッシュ・境界外読み取りの有無は `arboard` 3.6.1 のmacOSバックエンド実装まで踏み込んで確認していない(未検証、断定しない)。ただし①検証ロジック自体が自身の不変条件(`width*height*4 == bytes.len()`)をバイパスされる点、②`panic = "abort"` によりこの経路で万一パニックが起きた場合はコマンド単位のエラーではなく**アプリプロセス全体が即座に終了する**点は確定した事実であり、正常フローでは到達しない(現行フロントエンド `src/ipc/clipboard.ts` は常に実Canvasの `width`/`height` を渡すため無害)攻撃面ではあるが、Tauri公式の脅威モデル(IPCコマンドはwebview側を非信頼境界として扱い、コマンド側で全入力を検証すべき)に照らすと妥当な深刻度と判断した(前提条件: webview内で任意の `invoke()` 呼び出しができること。現状CSPは `default-src 'self'`・`unsafe-inline`/`eval`なしで、本アプリ内に既知のXSS経路は本レビューでは見つかっていない=即時の実悪用経路は無い)。
  **修正案**: `width.checked_mul(height).and_then(|v| v.checked_mul(4))` のようなchecked演算を使い、`None`(オーバーフロー)の場合は `ClipboardFallbackError`/`AppError` で拒否する。あわせて実運用上あり得ない大きさ(例: 1辺 65535px、あるいは `i32::MAX` 相当)の上限チェックを `parse_image_dimensions` に追加する。
  **修正難易度**: 低(`clipboard/mod.rs::validate_rgba` の1関数と、必要なら `commands.rs::parse_image_dimensions` の上限チェック追加のみ)。
  **偽陽性の可能性**: なし(オーバーフロー自体・release既定値・現行実装の欠如はソースとCargo公式ドキュメントで確認済み。下流の`arboard`挙動のみ未検証と明記)。

### MEDIUM(次回リリースまで)

- [ ] **[MEDIUM]** `src-tauri/src/capture/tempfile.rs:20-33`(`capture_dir`/`generate_capture_path`)・`src-tauri/src/tray.rs:160`(`app.exit(0)`) キャプチャ画像が一時ディレクトリに無期限に残置される(ARCH §12でMVP範囲外と決定済みの残存リスク評価)。
  **CVE/CWE**: CWE-459(Incomplete Cleanup)/ CWE-200(Exposure of Sensitive Information、機密情報を含みうる画面キャプチャが平文PNGとして永続)。
  **影響**: `generate_capture_path()` は `$TMPDIR/tadcap-captures/` 配下にPNGを生成するのみで、アプリのどのライフサイクル(クリップボードコピー成功後・履歴からの削除・トレイ「終了」`tray.rs:160`)にも削除処理が無い(`grep -rn "remove_file" src-tauri/src` で本番コードパスに削除呼び出しが無いことを確認。ヒットしたのは `capture/screencapture.rs` のテストコードのみ)。本アプリの主機能(画面キャプチャ→注釈)は仕様上パスワード入力欄・個人情報・機密資料等が写り込む可能性が高く、それが平文PNGとしてOS一時ディレクトリに蓄積し続ける。
  `$TMPDIR`(macOSのper-userテンポラリ、`/private/var/folders/.../T/`)自体はOSがユーザー専有(0700相当)で作成するため**他ユーザーからの読み取りは通常防がれる**が、①同一ユーザーで動く他プロセス(マルウェア・他アプリ・バックアップ/同期ツール等)からは自由に読み取れる、②アプリを閉じても・履歴から削除しても実体ファイルは残り続ける、③OS標準のperiodic一時消去に依存するため実際の残存期間が不定、という残存リスクがある。
  **修正案**: 最小対応として、トレイ「終了」(`tray.rs`の`TrayMenuAction::Quit`ハンドラ、`app.exit(0)`の直前)で `capture_dir()` 配下を削除する。中期対応として、クリップボードコピー成功後や履歴からの項目削除時に対応する一時ファイルも削除する設計へ拡張する(ARCH §12の再検討が必要な場合はPJM判断を仰ぐ)。
  **修正難易度**: 低(終了時一括削除のみなら)〜中(ライフサイクル全体の個別削除まで含めると)。
  **偽陽性の可能性**: なし(ARCH §12でMVP時点の既知の受容済みリスクと明記されている点は前提として尊重しつつ、今回のスキャン観点でリスクの大きさを再評価したもの。既存決定を覆す指摘ではなく、リリース前に人間判断者へ再提示すべき残存リスクとして記載)。
