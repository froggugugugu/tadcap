# PRD: 機密情報の自動マスキング(候補検出 + 一括モザイク)

> 生成元: `output/brainstorm/BRAINSTORM_auto-masking_2026-10-09.md`
> 生成日: 2026-10-09
> ステータス: Approved(2026-10-09 ゲート 1 通過。§10 の要確認 10 件は人間が決定済み)
> 関連: `output/prd/PRD_tadcap_mvp.md`(既存機能の PRD。本書の FR 番号は本書内だけで通用する。既存 PRD の FR を指すときは「MVP FR-008」のように書く)

## 1. 概要

### 1.1 背景・目的

キャプチャをチャットに貼る前の**隠し忘れ**を減らす。利用者がボタンを 1 回押すと、画像の文字を **Mac の中だけで**読み取り、機密らしい箇所を候補として印を付けて示す。利用者は不要な候補を外し、残りを**ボタン 1 つでまとめてモザイク**にできる。

- コンセプト: 隠し忘れの「最後の締め」。押せば、気づいていなかった機密に印が付き、安心して貼れる
- 位置づけ: 利用者が**意識して押す追加の便利機能**。自動で守る仕組みではない(2026-10-09 人間が確認)
- 精度の方針: **見逃しを避ける**(候補は多めに出し、人が外す)
- 差別化の看板機能(2026-10-09 人間が決定)。後続の柱「手順書モード」は別ブレストで扱う

### 1.2 スコープ

#### スコープ内

- ボタンを押した時だけ動く、画像内の文字の読み取り(端末内で完結。日本語・英語)
- 4 種の機密候補の検出: ①連絡先 ②認証情報 ③個人・社内の識別子 ④金額・口座(日本語の人名・会社名・住所を含む)
- 候補の印の表示、候補の個別の除外、残った候補の一括モザイク
- 一括モザイクは既存のモザイクツール(MVP FR-008)と同じ見た目・同じ強さで、取り消し(⌘Z)の 1 手として扱う
- 処理中の進捗表示
- 架空データだけで作る評価用画像セットと、種類ごとの検出率の計測

#### スコープ外

- 外部通信・クラウドの AI サービスの利用
- 読み取った文字・検出結果の保存(ファイル・設定・ログのいずれにも残さない)
- 顔・アイコン・ロゴなど**画像としての**検出(文字だけを対象にする)
- 「すべて隠しました」のように、隠し漏れが無いことを保証する表示
- 撮った直後の自動実行(ボタンを押した時だけ動く)
- 候補を残したまま ⌘C したときの警告・確認(今の動作と同じく、そのままコピーする)
- ボタンの押し忘れへの対策(使うかは利用者の判断)
- 利用者による独自の形式・語の登録、設定ファイルでの配布(後の版)
- 機密用の別の隠し方(塗りつぶし・より粗いブロック)・隠し方の選択
- モザイクツール全体の粗さの見直し(短い英数字を推測されうる点。必要なら別件で扱う)
- 日本語の固有名詞の精度を 70% より上げること(後の版)

## 2. 用語定義

| 用語 | 定義 |
| ---- | ---- |
| 自動マスキング | 本機能の総称。文字の読み取り → 候補の検出 → 候補の印の表示 → 個別の除外 → 一括モザイクの一連の流れ |
| 文字の読み取り | 画像に写った文字を、位置(画像上の領域)付きの文字列として取り出す処理。端末内で完結する |
| 候補(機密候補) | 機密らしいと判定された文字列とその画像上の領域。種類(下記 4 種の分類)を 1 つ持つ |
| 候補の種類 | ①連絡先 ②認証情報 ③識別子 ④金額・口座 の 4 分類 |
| 形が決まっているもの | 文字の並びの規則で判定できる候補。メール・電話番号・URL のクエリ・API キー/トークン・カード番号・口座番号・金額。検出率の目標 95% |
| 日本語の固有名詞 | 規則では判定できない日本語の人名・会社名・住所。検出率の目標 70% |
| 手がかり語 | 固有名詞や識別子の近くに現れやすい語。例: 「様」「さん」「株式会社」「〒」「社員番号」「パスワード」 |
| 候補の印 | 候補の領域に重ねて表示する枠と種類のラベル。画像には焼き込まず、コピー・履歴に含まれない |
| 候補を外す | 一括モザイクの対象から個別の候補を除くこと |
| 一括モザイク | 残っている(外していない)すべての候補の領域へ、既存のモザイクと同じモザイクを 1 回の操作でかけること |
| ベース | 既存の用語。表示中画像の元画像部分(`src/canvas/documentState.ts`)。モザイクはベースにだけかかり、上に乗る矢印・矩形・円のオブジェクトは隠れない(MVP FR-008 改訂) |
| 検出率 | 評価用画像セットの正解の領域のうち、候補として検出できた割合(判定方法は §8.3) |
| 評価用画像セット | 架空のデータだけで作った、検出率を測るための画像と正解データの組。リポジトリに含めてよい |

## 3. 機能要件

### FR-001: 自動マスキングの実行ボタン

- **概要**: 表示中の画像に対して自動マスキングを始めるボタンを置く。押した時だけ動く
- **ユーザーストーリー**: 利用者が、チャットに貼る前の最後の確認として、ボタン 1 回で機密らしい箇所を洗い出したい
- **受け入れ基準**:
  - [ ] 画像を表示しているとき、エディタ画面から自動マスキングのボタンを押せること
  - [ ] 画像を表示していないときは、ボタンが押せない状態であること
  - [ ] キャプチャの直後・履歴の切替時・アプリ起動時に、自動マスキングが勝手に始まらないこと
  - [ ] 処理中にボタンをもう一度押しても、処理が二重に走らないこと
  - [ ] 処理中に別の画像(新規キャプチャ・履歴の別項目)へ切り替えたとき、前の画像の結果が新しい画像に表示されないこと
- **画面・操作フロー**: ボタン押下 → 進捗表示(FR-008) → 候補の印の表示(FR-009)
- **データモデル変更**: なし(永続化しない。§5)
- **優先度**: Must

### FR-002: 端末内での文字の読み取り

- **概要**: 表示中の画像の文字を、位置付きで読み取る。日本語と英語を対象にする
- **ユーザーストーリー**: 情報システム部門が、画像や文字が外へ送られないことを利用者・社内に説明したい
- **受け入れ基準**:
  - [ ] 文字の読み取り・候補の検出の間に、アプリが外部と通信しないこと
  - [ ] 日本語(漢字・ひらがな・カタカナ)と英数字の混在した画面の文字を読み取れること
  - [ ] 読み取る対象は**ベース(元画像)**であり、利用者が載せた矢印・矩形・円のオブジェクトで読み取りが妨げられないこと
  - [ ] 読み取った文字・検出結果が、ファイル・設定・ログ(標準出力・標準エラーを含む)に出力されないこと
  - [ ] 読み取りに失敗したとき、利用者に失敗したことを伝え、画像は変更されないこと
- **画面・操作フロー**: FR-001 の内部処理(利用者には進捗表示だけが見える)
- **データモデル変更**: なし
- **優先度**: Must

### FR-003: 連絡先の検出

- **概要**: メールアドレス・電話番号を候補として検出する
- **ユーザーストーリー**: 利用者が、画面に写り込んだ自分や顧客の連絡先を隠し忘れないようにしたい
- **受け入れ基準**:
  - [ ] メールアドレスを「連絡先」の候補として検出すること
  - [ ] 日本の電話番号(固定・携帯。ハイフン有無・括弧付きの表記)を「連絡先」の候補として検出すること
  - [ ] 評価用画像セットで、メール・電話番号それぞれの検出率が 95% 以上であること
- **画面・操作フロー**: FR-009 の候補の印として表示
- **データモデル変更**: なし
- **優先度**: Must

### FR-004: 認証情報の検出

- **概要**: API キー・トークン・パスワードらしき文字列・URL のクエリを候補として検出する
- **ユーザーストーリー**: 利用者が、設定画面やログに写った秘密の文字列をうっかり共有しないようにしたい
- **受け入れ基準**:
  - [ ] 広く使われるサービスの API キー・アクセストークンの形(固有の接頭辞を持つ英数字列・長いランダムな英数字列)を「認証情報」の候補として検出すること
  - [ ] 「パスワード」「password」「pass」「secret」「token」などの手がかり語に続く文字列を「認証情報」の候補として検出すること
  - [ ] URL のクエリ部分を「認証情報」の候補として検出すること(隠すのは**クエリ部分(`?` 以降)だけ**。§10 #3)
  - [ ] 評価用画像セットで、API キー/トークン・URL のクエリそれぞれの検出率が 95% 以上であること
- **画面・操作フロー**: FR-009 の候補の印として表示
- **データモデル変更**: なし
- **優先度**: Must

### FR-005: 個人・社内の識別子の検出(形が決まっているもの)

- **概要**: 社員番号・顧客番号など、手がかり語を伴う番号を候補として検出する
- **ユーザーストーリー**: 利用者が、社内システムの画面に写った社員番号・顧客番号を隠し忘れないようにしたい
- **受け入れ基準**:
  - [ ] 「社員番号」「顧客番号」「会員番号」「ID」などの手がかり語に続く英数字を「識別子」の候補として検出すること
  - [ ] 評価用画像セットで、手がかり語付きの番号の検出率が目標 **70%**(§10 #5)以上であること
- **画面・操作フロー**: FR-009 の候補の印として表示
- **データモデル変更**: なし
- **優先度**: Must

### FR-006: 金額・口座の検出

- **概要**: カード番号・口座番号・金額を候補として検出する
- **ユーザーストーリー**: 利用者が、請求・決済の画面に写った番号や金額を隠し忘れないようにしたい
- **受け入れ基準**:
  - [ ] カード番号(13〜19 桁、区切りの空白・ハイフン有無)を、チェックディジットが正しい場合に「金額・口座」の候補として検出すること。4 桁 × 4 組の区切りがある 16 桁は、チェックディジットが合わなくても候補にする(読み取りの 1 字誤読で見逃さないため。2026-10-09 改訂、ARCH §15 #6)
  - [ ] 「口座番号」などの手がかり語に続く番号を「金額・口座」の候補として検出すること
  - [ ] 金額を「金額・口座」の候補として検出すること(対象は**「¥」「円」「$」などの通貨記号・単位が付いた数値だけ**。§10 #1)
  - [ ] 評価用画像セットで、カード番号・口座番号・金額それぞれの検出率が 95% 以上であること
- **画面・操作フロー**: FR-009 の候補の印として表示
- **データモデル変更**: なし
- **優先度**: Must

### FR-007: 日本語の固有名詞の検出

- **概要**: 日本語の人名・会社名・住所を候補として検出する。最初の版に入れるが目標は低め(70%)とし、精度は後の版で高める
- **ユーザーストーリー**: 利用者が、顧客名・取引先名・住所の写り込みに気づけるようにしたい
- **受け入れ基準**:
  - [ ] 日本語の人名を「識別子」の候補として検出すること(手がかり語「様」「さん」「氏」等を伴わない人名も対象)
  - [ ] 会社名(「株式会社」「(株)」「有限会社」等を伴うもの)を「識別子」の候補として検出すること
  - [ ] 住所(「〒」・郵便番号・都道府県名から始まるもの等)を「連絡先」の候補として検出すること
  - [ ] 評価用画像セットで、人名・会社名・住所それぞれの検出率が 70% 以上であること
  - [ ] 英字表記の人名(例: 「Taro Yamada」)も対象にすること(目標 70%。§10 #6)
- **画面・操作フロー**: FR-009 の候補の印として表示
- **データモデル変更**: なし
- **優先度**: Must

### FR-008: 処理中の進捗表示

- **概要**: 読み取り・検出の処理中であることを利用者に示す
- **ユーザーストーリー**: 利用者が、待っている間に固まったのか処理中なのかを区別したい
- **受け入れ基準**:
  - [ ] ボタンを押してから候補の印が出るまでの間、処理中であることが画面に表示されること
  - [ ] 処理が終わったとき(成功・失敗とも)、処理中の表示が消えること
  - [ ] 処理中もアプリの画面が応答し続けること(ウィンドウの移動・履歴の閲覧ができる)
- **画面・操作フロー**: ボタン押下 → 処理中の表示 → 結果表示
- **データモデル変更**: なし
- **優先度**: Must

### FR-009: 候補の印の表示

- **概要**: 検出した候補の領域に枠と種類のラベルを重ねて表示する
- **ユーザーストーリー**: 利用者が、どこが・なぜ候補になったかを一目で確認したい
- **受け入れ基準**:
  - [ ] すべての候補の領域に印(枠)が表示されること
  - [ ] 各候補の種類(連絡先・認証情報・識別子・金額・口座)が、印から判別できること
  - [ ] 候補の印は画像のピクセルに焼き込まれないこと(⌘C のコピー結果・履歴のサムネイル・履歴画像に印が含まれない)
  - [ ] 候補が 0 件のとき、0 件であることを伝えること。その文言は「すべて隠した」「安全」など、隠し漏れが無いことを保証する表現を含まないこと
  - [ ] 候補の件数が表示されること
  - [ ] ウィンドウの拡大縮小で画像の表示サイズが変わっても、印が候補の領域からずれないこと
- **画面・操作フロー**: 結果表示 → 利用者が確認 → FR-010 で外す → FR-011 で一括モザイク
- **データモデル変更**: なし(画面上の一時的な状態。§5)
- **優先度**: Must

### FR-010: 候補を個別に外す

- **概要**: 不要な候補を一括モザイクの対象から外す。外した候補は戻せる
- **ユーザーストーリー**: 利用者が、隠さなくてよい箇所(公開情報・必要な情報)まで隠してしまうのを防ぎたい
- **受け入れ基準**:
  - [ ] 候補を 1 件ずつ外せること(**画像上の印をクリックすると外れ、もう一度クリックすると戻る**。§10 #2)
  - [ ] 外した候補と残っている候補が見た目で区別できること
  - [ ] 外した候補を、一括モザイクの前なら元に戻せること
  - [ ] 外した候補は一括モザイクの対象にならないこと
- **画面・操作フロー**: 候補の印の表示中に、候補ごとに外す/戻す
- **データモデル変更**: なし
- **優先度**: Must

### FR-011: 一括モザイク

- **概要**: 残っている候補の領域すべてに、既存のモザイクツールと同じモザイクを 1 回の操作でかける
- **ユーザーストーリー**: 利用者が、候補を 1 つずつ手でモザイクにする手間を省きたい
- **受け入れ基準**:
  - [ ] ボタン 1 回で、外していないすべての候補の領域がモザイクになること
  - [ ] モザイクの見た目・粗さ(ブロックサイズの算出)が、既存のモザイクツール(MVP FR-008)と同じであること
  - [ ] モザイクは既存と同じくベースのピクセルに焼き込まれ、⌘C のコピー結果に反映されること
  - [ ] 一括モザイクが取り消し(⌘Z)の 1 手として扱われ、1 回の取り消しで全候補分が元に戻ること。やり直し(⇧⌘Z)で再びかかること
  - [ ] 候補の領域が文字の端で切れないよう、領域に余白を持たせてモザイクをかけること
  - [ ] 一括モザイクの後、候補の印が消えること
  - [ ] 残っている候補が 0 件のときは、一括モザイクのボタンが押せないこと
- **画面・操作フロー**: 候補の印の表示中に一括モザイクのボタンを押す → モザイクが反映され印が消える
- **データモデル変更**: なし(既存の取り消しの仕組みの中で 1 手を作る。§5)
- **優先度**: Must

### FR-012: 候補を出したままの操作

- **概要**: 候補の印を出したまま一括モザイクをせずに他の操作をしたときの動きを定める
- **ユーザーストーリー**: 利用者が、候補を確認しただけで(隠さずに)そのまま貼りたいときに邪魔されたくない
- **受け入れ基準**:
  - [ ] 候補の印を出したまま ⌘C(またはコピーボタン)を押すと、警告・確認なしに、印を含まない画像がコピーされること(今の動作と同じ)
  - [ ] 候補の印を消して自動マスキングをやめる操作があること
  - [ ] 別の画像(新規キャプチャ・履歴の別項目)へ切り替えたとき、候補を**破棄する**こと(戻ったらボタンを押し直す。§10 #4)
- **画面・操作フロー**: 候補の印の表示中に ⌘C / 取り消し操作 / 画像切替
- **データモデル変更**: なし
- **優先度**: Must

### FR-013: 種類ごとの印の表示/非表示

- **概要**: 候補の種類ごとに印をまとめて表示/非表示(= 外す/戻す)できる
- **ユーザーストーリー**: 利用者が、金額など大量に出る種類をまとめて外したい
- **受け入れ基準**:
  - [ ] 候補の種類ごとに、その種類の候補をまとめて外す/戻すことができること
- **画面・操作フロー**: 候補の印の表示中に種類ごとに切り替え
- **データモデル変更**: なし
- **優先度**: Could(後の版。§10 #7)

### FR-014: 自動マスキングのショートカット

- **概要**: 自動マスキングの開始をキーボードで行える
- **ユーザーストーリー**: 利用者が、貼る前の確認をキー操作だけで済ませたい
- **受け入れ基準**:
  - [ ] エディタ画面にフォーカスがあるとき、決まったキー操作で FR-001 と同じ処理が始まること
  - [ ] 既存のショートカット(⌘C・⌘Z・⇧⌘Z・キャプチャ用のグローバルショートカット)と衝突しないこと
- **画面・操作フロー**: キー押下 → FR-001 と同じ
- **データモデル変更**: なし
- **優先度**: Should(最初の版に入れる。§10 #7)

## 4. 非機能要件

### NFR-001: 処理時間

- **カテゴリ**: パフォーマンス
- **要件**: フル HD 程度(1920×1080 px)の画像で、ボタンを押してから候補の印が出るまで **3 秒以内**。Retina の全画面キャプチャなど、より大きい画像は**目標を設けず**、処理中の表示があればよい。実測して記録する(§10 #8)
- **計測方法**: 評価用画像セットのうちフル HD の画像で、ボタン押下から印の表示完了までを計測する(対応する最も遅い想定の機種での中央値・最大値を記録)。計測の作法は既存の NFR-001 中間計測(`scripts/latency-summary.mjs`)に合わせる

### NFR-002: 端末内での完結・非保存

- **カテゴリ**: セキュリティ
- **要件**:
  - 文字の読み取り・検出の間に外部と通信しない
  - 読み取った文字・検出結果をファイル・設定・ログに出さない。メモリ上の文字列は処理後に保持しない
  - 新たなネットワーク権限・外部通信の許可を追加しない(既存の CSP `connect-src` を広げない)
- **計測方法**: ①CSP・権限設定(`src-tauri/tauri.conf.json`・`src-tauri/capabilities/default.json`)の差分レビュー ②ログ出力箇所に読み取り文字・検出文字列が渡らないことのコードレビュー ③実機で処理中に通信が発生しないことの確認(手動)

### NFR-003: 検出率

- **カテゴリ**: 品質(精度)
- **要件**: 評価用画像セットで、候補の種類(細分)ごとに **形が決まっているもの 95% 以上 / 日本語の固有名詞 70% 以上**
- **計測方法**: §8.3 の評価手順で、種類ごとの検出率を算出して記録する。誤検出(正解でない候補)の件数は目標を設けず参考値として記録する(見逃しを避ける方針のため)

### NFR-004: 対応 OS・依存

- **カテゴリ**: 保守性
- **要件**: 既存の対応 OS(macOS 14 以降、`src-tauri/tauri.conf.json` の `minimumSystemVersion`)を変えない。日本語の文字の読み取りが macOS 14 で使えること
- **計測方法**: macOS 14 の実機または仮想環境で FR-002 を確認する

### NFR-005: 保証しない表現

- **カテゴリ**: ユーザビリティ
- **要件**: 画面の文言・README・紹介ページで、自動マスキングを「自動で守る」「すべて隠す」ものとして説明しない。利用者が最終確認する補助機能であることを示す
- **計測方法**: 追加・変更した文言のレビュー

## 5. データモデル

### 新規スキーマ

永続化するデータは**追加しない**(NFR-002)。画面上の一時的な状態として、次の情報を表示中の画像に対してだけメモリ上で持つ。

| 状態 | 内容 | 寿命 |
| ---- | ---- | ---- |
| 候補の一覧 | 候補ごとに: 画像上の領域(画像のピクセル座標の矩形)・種類(4 分類)・外したかどうか | 一括モザイク・やめる操作・画像の切替(§10 #4)で破棄 |
| 処理の状態 | 未実行 / 処理中 / 結果表示中 / 失敗 | 同上 |

- 候補の一覧に**読み取った文字列そのものは持たない**こと(印の表示・一括モザイクに不要なため)【仮定】。種類のラベル表示に文字列が要る場合は設計で再検討する
- 座標は既存のツールと同じく画像の実ピクセル基準とする(`src/canvas/coords.ts` の `Rect`)

### 既存スキーマ変更

| -------- | ---------- | -------- | ---------- |
| 取り消しのコマンド(`DocumentCommand`、`src/canvas/commands.ts`) | なし(既存の `group` / `pixels` を使う想定) | 一括モザイクを 1 手として積む。新しい種類を追加するかは設計で決める | 永続化しないため影響なし |
| 履歴の退避(`src/history/documentArchive.ts`) | なし | 一括モザイクの取り消し用ピクセルも、既存の上限(`ARCHIVED_UNDO_BYTES_LIMIT`)の対象になる | 永続化しないため影響なし |
| 設定(`src-tauri/src/settings.rs`) | なし(FR-014 を入れ、キーを変更可能にする場合のみ追加の可能性) | — | 追加する場合は未設定時に既定値で動くこと |

- **アクセシビリティ**: 新しいボタンは既存のアイコンボタンと同じく `aria-label` / ツールチップを持つ

## 7. 技術的考慮事項

### 7.1 アーキテクチャへの影響

- 文字の読み取りは webview(TypeScript)から OS の機能を直接呼べないため、Rust 側の新しい IPC コマンド(またはそれに準ずる仕組み)が必要になる。画像はベースの PNG/ピクセルを渡す
- 検出(規則・手がかり語・固有表現の判定)を Rust 側と TypeScript 側のどちらに置くかは設計で決める。どちらに置いても、DOM 非依存の純粋関数としてユニットテストできる形にする(既存の作法: `mosaicTool.ts` の純粋関数 + 手動確認)
- 一括モザイクは既存の `pixelateImageData()` / `mosaicBlockSize()`(`src/canvas/tools/mosaicTool.ts`)と `applyBaseEdit()` 相当(`src/canvas/documentState.ts`)を再利用し、複数の領域を 1 手(`group` コマンド)にまとめる想定
- 処理中の画像の切替との競合は、既存のキャプチャ競合対策(`e2e/capture-race.spec.ts` で検証している種類)と同じ考え方で、結果を受け取る時点の表示中画像を照合する

### 7.2 技術選定の選択肢(決定は `/architecture`)

| 論点 | A 案 | B 案 | 判断材料 |
| ---- | ---- | ---- | -------- |
| 文字の読み取りの実装場所(ブレスト #7) | Rust から OS の文字認識機能を Objective-C ブリッジ経由で呼ぶ(既存で `objc2` / `objc2-app-kit` を使用中) | Swift で書いた小さな補助プロセスを同梱し、Rust から起動する | A: 追加プロセス不要。ブリッジ用クレートの追加要否の確認が必要 / B: OS の API を素直に書ける。ビルド・署名・公証の手順が増える(`scripts/package-mac.sh`・`release.yml`) |
| 日本語の固有名詞の判定 | OS の固有表現抽出機能(言語処理)を使う | 手がかり語 + 小さな辞書(姓・都道府県等)による規則 | A: 追加データ不要だが日本語の精度が未知 / B: 精度を調整しやすいが辞書の出典・ライセンス確認が必要(`/legal-check`)。併用も可 |
| 検出処理の置き場所 | Rust(読み取りと同じ側で完結し、文字列を webview へ渡さない) | TypeScript(既存のテスト基盤 Vitest を使える) | A: 文字列が IPC を通らず NFR-002 を説明しやすい / B: 規則の変更・テストが手軽 |

- 【前提】日本語の文字の読み取りは macOS 13 以降の OS 標準機能で使え、対応 OS(14 以降)を満たす。追加のモデル同梱は不要(ブレスト §2)
- 【前提】形が決まっているものは正規表現とチェックディジット(カード番号の Luhn)で判定できる(ブレスト §2)

### 7.3 依存方向

- 既存の層: `ui/` → `canvas/` → `ipc/`(Tauri 呼び出し)。検出結果の状態は `canvas/` 配下の薄いストア(既存 `documentState` と同じ作法)とし、`ui/` から参照する。`canvas/` から `ui/` への依存は作らない
- Rust 側は新しいモジュール(例: 文字の読み取り)を `commands.rs` から呼ぶ形にし、`capture/` など既存モジュールとの循環を作らない
- 依存方向の検出コマンドは未導入(project-config.md §3)のため、レビューで確認する

### 7.4 既存の数値との整合

- 既存モザイクのブロックサイズは「画像の対角線 × 0.008、下限 12px・上限 64px」(`src/canvas/tools/mosaicTool.ts:95` `mosaicBlockSize()`)。フル HD で約 18px。ブレストの「画像幅の約 0.9%」は概算であり、実装は上記の式に従う
- 取り消しは 30 手まで(`UNDO_STACK_LIMIT`、`src/canvas/undoStack.ts:25`)。一括モザイクは 1 手として数える

## 8. テスト戦略

### 8.1 ユニットテスト(Vitest / cargo test)

- 種類ごとの検出規則(メール・電話・API キー/トークン・手がかり語+文字列・URL のクエリ・カード番号の Luhn・口座番号・金額)の境界値: 区切り文字の有無、全角/半角、桁数の上下限、Luhn 不正、隣接文字との境界
- 手がかり語による識別子・会社名・住所の判定
- 候補の状態遷移(未実行 → 処理中 → 結果表示中 → 一括モザイク/やめる/切替で破棄)、外す/戻すの切替
- 候補領域への余白付けと画像範囲へのクリップ
- 一括モザイクが 1 手の取り消しになり、取り消し・やり直しで全候補分が戻る/かかること(既存の `PixelStore` の偽物を使う)

### 8.2 E2E テスト(Playwright、既存の IPC モック方式)

- 文字の読み取りの IPC をモックし、固定の候補を返して: 印の表示 → 個別に外す → 一括モザイク → ⌘Z で戻る、の一連の流れ
- 候補を出したまま ⌘C したとき、コピーされる画像に印が含まれないこと
- 処理中に新規キャプチャ・履歴切替をしたとき、古い結果が出ないこと
- 候補 0 件のときの表示(保証の表現を含まない)
- 見た目の確認は既存の `e2e/screenshots/*.visual.ts` の作法で印の表示を追加
- OS の文字認識そのものは E2E の対象外(既存方針: OS ネイティブ導線は対象外)

### 8.3 評価用画像セットと検出率の計測(NFR-003)

- **データ**: 架空のデータだけで作る(実在の個人情報・社内情報は使わない)。リポジトリに入れてよい
- **構成(§10 #9 で提案どおりに決定)**:
  - 画像 20 枚以上。ダミーの社内システム・メール・設定画面・請求画面・ターミナル風画面などを模した構成
  - 正解の件数: 形が決まっているものは細分ごとに 40 件以上、日本語の固有名詞は人名・会社名・住所それぞれ 30 件以上
  - 解像度はフル HD と Retina 相当の両方、背景は明るい画面・暗い画面の両方、文字サイズは小・中・大を含める
  - 正解データは「画像・領域(矩形)・種類」の組で持つ
- **判定**: 正解の領域が、候補の領域(余白込み)にどれだけ覆われたかで判定する(基準は**正解の領域が 100% 覆われること**。一部でもはみ出せば見逃し。§10 #10)
- **実行**: 実機(macOS)で OS の文字認識を通して計測する。CI(実機の文字認識が使えない環境)では回さず、計測結果を `testreport/` に、まとめを `output/reports/` に残す【仮定】

### 8.4 手動確認

- 実機での処理時間(NFR-001)、通信が発生しないこと(NFR-002)、macOS 14 での日本語の読み取り(NFR-004)
