# ADR-002: トリミングを取り消し 1 手の操作とし、注釈の大きさの基準を保つ

## ステータス

Accepted(2026-10-10。ゲート 2 で `output/design/ARCH_quick-edits.md` を承認し、§15 の要確認 4 件を人間が推奨案で決定。実装はまだ。実装で前提が崩れた場合は本 ADR を更新する)

## コンテキスト

小さな編集機能(`output/prd/PRD_quick-edits.md`)のトリミング(FR-005〜FR-007)は、**ベースの画像の大きさが変わる初めての操作**である。今のコードは「画像の大きさは編集中に変わらない」ことを暗黙の前提にしており、座標や大きさを持つ機能のすべてが影響を受ける(ARCH §7.3 の影響表、PRD §7.1・§11 で影響度「高」)。

| 機能 | トリミングで起きること(何もしない場合) |
| ---- | ---------------------------------------- |
| 注釈の座標 | 切り詰めた画像の左上が原点になり、注釈が別の場所を指す |
| 注釈の大きさ | 太さ・文字の大きさは描くたびに「今の画像の対角線」から計算している(ARCH §1.3 #3 が示す `arrowTool.ts:122-125`・`textLayout.ts:61-68`・`rectangleTool.ts:72-75`)。画像が小さくなると、描いた注釈が細く・小さく変わる |
| モザイクの粗さ | 同じく画像の対角線で決まる。5K の全画面(ブロック 47px)を 1200×800 に切った後のモザイクは 12px になり、文字が読めてしまうおそれがある |
| 取り消し | 既存の `pixels` / `flatten` は同じ大きさの矩形の差し替えで、大きさを変えられる種類が無い。トリミングより前の手は元の大きさの座標を持つ |
| 履歴への退避 | 取り消しのピクセルは上限 8MB(`ARCHIVED_UNDO_BYTES_LIMIT`)まで退避される |
| 移動の範囲 | `moveShape()` は注釈が常に画像の内側にある前提で範囲を `[-左端, 幅-右端]` に絞る。一部がはみ出した注釈では範囲が逆転する |
| 50 個の上限 | 範囲外の注釈が見えないまま上限を食うと、古い注釈の焼き込みが早まる |
| 自動マスキング・表示の倍率・オーバーレイ | 候補の座標・表示 canvas の大きさが変わる |

PRD 側の決定・制約:

- 範囲外へ完全に出た注釈は消し、確定と同じ 1 手にする(⌘Z で戻る。PRD §10 #5 A)
- 描いた注釈の見た目の大きさはトリミングの前後で変えない(FR-006【仮定】)
- トリミングより前の操作も、トリミングを取り消した後に続けて取り消せる(FR-007)。履歴を切り替えて戻ったとき、8MB の上限を超える分が取り消せなくなるのは許容する(FR-007)
- 依存を増やさない(NFR-003)

PRD §7.2 は取り消しの方式を A 案(ベースとオブジェクト全体を退避する新しいコマンド)と B 案(ベースの差し替え + `update` + `remove` を `group` にまとめる)の 2 つで示し、決定を設計に委ねていた。

## 判断

**トリミングは「ベース全体を入れ替える新しいコマンド `crop`」と注釈のずらし(`update`)・範囲外の削除(`remove`)を 1 つの `group` に積んだ取り消し 1 手の操作とし、切る前に描いた注釈は切る前の大きさの基準を保ち、モザイクの粗さは常に撮った時点の画像の大きさで決める。**

詳細(ARCH §1.3 #1〜#7・§5.3・§5.4・§15 の決定):

| 項目 | 決定 | 根拠 |
| ---- | ---- | ---- |
| 取り消しの手の形 | `group[crop, update…, remove…]`。`crop` は `{ type: "crop"; rect; image }` で、`image` は「反対側のベース全体」。取り消し・やり直しのたびに `PixelStore.swapAll(image)` で今のベース全体と入れ替える(既存の `pixels` と同じ入れ替え方式) | ベースの大きさを変えられるのは新しい種類だけ。注釈は既存の `update` / `remove` を再利用でき、`group` の逆順取り消し(ARCH が示す `commands.ts:120-130`)で「消した注釈を戻す → 形を戻す → 元の大きさのベースに戻す」の順序が保たれる。`update` / `remove` は `id` で対象を探すため、ベースの大きさと独立に戻る |
| 入れ替えの手段 | `PixelStore.swapAll(image)`: ベースと表示 canvas を同時に `image` の大きさにして書き、前のベース全体を返す | 表示 canvas とベースの大きさが違うと合成を描かない作りのため、両方を同時に変える口が要る |
| 範囲外の注釈 | 完全に出た注釈は同じ `group` に `remove` を積む。完全に出たかは描画範囲(`shapeUndoRect()`、線の太さ・影込み)と範囲の重なりで判定する | 見た目と一致する判定にする(線の端が範囲に少し掛かる矢印は残る)。PRD §10 #5 A |
| 何もしない範囲 | 整数化した範囲の幅・高さが 0、または画像全体と同じなら手を積まない | 空の手で取り消しの 30 手を消費しない |
| 注釈の大きさの基準(§15 #1 B) | 注釈に任意の `styleBasis`(大きさを決める対角線)を持たせる。トリミングの確定で残った注釈にだけ「切る前の対角線」を付け、2 回目以降のトリミングでは既に付いた値を変えない。切った後に新しく描く注釈は付けず、今の画像の大きさで決める。計算は `shapeStyleDiagonal(shape, w, h) = shape.styleBasis ?? hypot(w, h)` に一本化する | 描いた注釈の見た目を変えない(FR-006)と、「撮る → 切る → 描く」で最初からその範囲を撮った場合と同じ大きさになることの両立 |
| モザイクの粗さ(ARCH §1.3 #4) | ドキュメントごとに撮った時点の大きさ `captureSize` を持ち、`mosaicBlockSize()` は常にそれで決める。トリミングでは変えない。自動マスキングの一括モザイクも同じ。履歴の退避(`DocumentSnapshot`)にも入れる | 画面上の文字の画素数はトリミングで変わらない。今の画像で決めると、切った後のモザイクが細かくなり隠す目的に反する |
| はみ出した注釈の移動(ARCH §5.3) | `moveShape()` の範囲を `[min(0, -左端), max(0, 幅 - 右端)]` にする | 画像の内側の注釈は今と同じ範囲のまま。はみ出した注釈は「はみ出しを増やさない方向」に動かせ、範囲の逆転で跳ばない |
| 番号スタンプと穴(§15 #2 B・#3 A、PRD §10 #8 A) | 50 個の上限による焼き込みの対象から、穴(スポットライト)と番号スタンプを外す。焼き込める注釈が無ければ 51 個目は追加せず「注釈は 50 個までです」と知らせる | トリミングで消えた番号の分は `id` の順位から求める番号で自動的に詰まり、取り消しで戻る。番号を焼き込むと、番号の固定・飛び・台帳がトリミングの取り消しとも絡み、状態が増える。穴を焼き込むと暗さが二重になる |
| 範囲の指定中の ⌘Z(§15 #4 A) | 指定をやめるだけ(画像は変えない。もう一度押すと通常の取り消し) | 1 回のキーで起きることを 1 つにする |

## 検討した代替案

### 代替案 A: 注釈を描く前だけトリミングできるようにする

- **メリット**: 注釈の座標・大きさ・番号・上限との関係を考えなくてよい。取り消しはベースの入れ替えだけで済む
- **デメリット**: 「描いた後で切り抜く」(FR-006 のユーザーストーリー)ができない。描いた後に切りたくなったら、注釈を消して切ってから描き直すことになる
- **不採用理由(却下)**: PRD FR-006 の要件(描き直さずに済ませたい)を満たさない

### 代替案 B: ベースとオブジェクト全体を丸ごと退避する新しいコマンド(PRD §7.2 A 案)

- **メリット**: 1 種類のコマンドで完結し、単純。注釈のずらし・削除を個別の手として組み立てなくてよい
- **デメリット**: 注釈全体の写しを持つ新しい種類になり、取り消しの単位が既存(`update` / `remove` の組み合わせ)と揃わない。オブジェクト全体を差し替えるため、退避・選択の整理の扱いを別に作る必要がある
- **不採用理由**: 既存の `update` / `remove` / `group` を再利用できる採用案のほうが、新しい種類が「ベースの大きさを変える」1 つに絞られ、既存の偽の `PixelStore` でテストを書ける(ARCH §1.3 #1)。退避のバイト数の大半はベース全体で、どちらの案でも変わらない

### 代替案 C: 切り落とした部分だけを退避する(差分で退避)

- **メリット**: 退避が小さくなる(範囲の外の帯 4 本分だけ)。小さく切るほど差は小さいが、端を少し切るだけなら大きく減る
- **デメリット**: 取り消しで「元の大きさの canvas を作り、残した部分と 4 本の帯を組み立てる」処理が要り、入れ替えだけの既存の方式(`pixels` と同じ)から外れる。範囲の位置によって帯の数・形が変わり、テストの組み合わせが増える
- **不採用理由(見送り)**: 30 手の上限の中では表示中のメモリは許容範囲(PRD §11 の「中」のリスクの範囲)で、まず単純な入れ替えを選ぶ。メモリで困った場合は、ベース全体を `ImageData` ではなく画面外の canvas のまま持つ案(ARCH §16)と合わせて検討する

### 代替案 D: 大きさの基準をドキュメント全体で撮った時点に固定する(§15 #1 A)

- **メリット**: 基準が 1 つで単純。切る前・切った後に描いた注釈の太さが常に揃う。モザイクと同じ考え方で説明しやすい
- **デメリット**: 5K の全画面を 1200×800 に切ってから描くと、矢印が 72px(上限)・文字が 128px になり、その範囲を最初から撮った場合(19px・35px)と大きく違う
- **不採用理由(却下)**: 「撮る → 切る → 描く」という自然な流れで注釈が極端に太く・大きくなる

### 代替案 E: 大きさの基準を固定しない(§15 #1 C)

- **メリット**: 状態が増えない(今の作りのまま)
- **デメリット**: 描いた後に切ると、注釈が細く・小さく変わる。上限で既に焼き込まれた注釈(ベースの一部として前の大きさのまま)とも食い違う
- **不採用理由(却下)**: PRD FR-006 の【仮定】(前後で見た目の大きさが変わらない)を外すことになる

### 代替案 F: モザイクの粗さを今の画像の大きさで決める(既存のまま)

- **メリット**: 状態(`captureSize`)が増えない
- **デメリット**: 切った後のモザイクが細かくなり、隠した文字が読めてしまうおそれがある
- **不採用理由(却下)**: モザイクの目的(隠す)に反する。注釈の大きさとは違い、どの案でも撮った時点の大きさで決める

## 影響

### ポジティブな影響

- トリミングが 1 手で取り消せ、トリミングより前の手(モザイク・注釈の追加など)も元の大きさに戻ってから適用されるため、そのまま正しく戻る(FR-007)
- 新しいコマンドの種類は `crop` 1 つだけで、注釈のずらし・削除は既存の取り消しの経路に乗る。純粋関数(`normalizeCropRect()`・`planCrop()`・`shapeStyleDiagonal()`)と偽の `PixelStore` でユニットテストできる
- 描いた注釈の見た目と、モザイクの隠す強さがトリミングで変わらない
- 番号は `id` の順位から求めるため、トリミングで消えた番号の分は自動で詰まり、取り消しで元に戻る(PRD §10 #5 の影響範囲)

### ネガティブな影響・リスク

- **メモリ**: `crop` は取り消し側に切る前のベース全体(RGBA)を持つ(ARCH §6.4)

  | 撮った画像 | ベース全体 |
  | ---------- | ---------- |
  | 1920×1080 | 約 8.3MB |
  | 3024×1964(倍率 2 の 14 型相当の全画面) | 約 23.8MB |
  | 5120×2880 | 約 59.0MB |

  表示中の画像では 30 手(`UNDO_STACK_LIMIT`)の中に収まり、何度か切っても数十〜百数十 MB にとどまる。
- **履歴を切り替えると古い手が取り消せなくなる**: 履歴へ退避するときの上限は 8MB で、フル HD のベース全体でもほぼ届く。`trimUndoToBudget()` が古い手から捨て、`crop` が捨てられるとそれより古い手も一緒に捨てられる(途中だけ抜かない既存の作り)。戻った後はトリミング後の画像で続きの操作・取り消しはできる。PRD FR-007 でこの範囲は許容している
- **切る前と切った後で注釈の太さが違いうる**: 切る前に描いた注釈は前の基準、切った後に描いた注釈は今の基準で決まるため、同じ画像の上で太さが揃わないことがある(§15 #1 B の欠点として受け入れた)
- **状態が増える**: 注釈の `styleBasis`、ドキュメントの `captureSize` を持ち、退避にも含める。今後、大きさを計算する箇所は画像の今の大きさを直接使わず `shapeStyleDiagonal()`・`captureSize` を通す必要がある(ARCH §14 で `docs/development-patterns.md` の規約にする)
- **番号スタンプと穴だけで 50 個になると、51 個目を追加できない**(§15 #3 A)。手順として 50 個は実用の範囲外と判断した

### 未確認の仮定

- 【仮定】撮影コマンドが、倍率 2 の画面では 144dpi、倍率 1 の画面では 72dpi の解像度の情報(PNG の pHYs チャンク)を書く(ARCH §1.3 #10・§15)。トリミングは倍率を変えず、縮めてコピーは切り詰め後の画像にも同じ倍率で効く(FR-007)ため、本 ADR の判断はこの仮定に依存しない。外れた場合は倍率が「不明」となって縮めない側に倒れ(今の動作と同じ)、ARCH §16 の代替(撮影の終わりのマウスの位置の画面の倍率を OS から取る)を人間に諮る。実装の最初に実機で確かめる(ARCH §10.3)

### 関連する判断

- [ADR-001](ADR_001_text-recognition.md): 自動マスキングの検出方式。候補はベースの座標を持つため、ドキュメントの大きさが変わったら候補を捨てる防御を `ui/autoMask.ts` に置く(FR-007)。確認中はトリミングを始められない
- 本 ADR で扱わない判断: 設定ファイルを 1 項目だけ読み書きする `SettingsStore`(ARCH §1.3 #13)、スポットライトの暗さの塗り方(#8・#9)、縮める場所(#12)は ARCH に記録した
