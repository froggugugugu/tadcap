# ADR-001: 自動マスキングの検出を、端末内の文字認識 + 規則ベースで行う

## ステータス

Accepted(2026-10-09。ゲート 2 で方式を承認 → 実装・評価・ホールドアウト 3 回の結果を受けて、人間が「この方式で得意・苦手を明示して出す」と決定)

## コンテキスト

自動マスキング(`output/prd/PRD_auto-masking.md`)は、キャプチャ画像の中の機密らしい箇所(連絡先・認証情報・識別子・金額や口座)に印を付け、利用者が確かめてからまとめてモザイクをかける機能である。実現には「画像の文字を読む」「読んだ文字から機密らしい箇所を決める」の 2 つが要る。

制約:

- **端末内で完結すること**(PRD NFR-002)。Tadcap は「外部との通信なし」「何も残さない」を約束しており(README・紹介ページ)、機密を含みうる画像を外へ送る方式は約束と矛盾する
- **読み取った文字を残さないこと**(NFR-002)。IPC・webview・ファイル・ログ・パニックの文言のどこにも出さない
- **依存を増やさない・配布手順を変えない**(ARCH §15 の条件)。署名・公証付きの配布(`docs/release-notarization.md`)を崩さない。新しい npm パッケージは足さない
- **日本語の画面で使えること**。対象は日本語と英語が混ざる業務画面
- **速いこと**: フル HD で 3 秒以内(NFR-001)。対応 OS は macOS 14 以降(NFR-004)
- **保証しないこと**(NFR-005): 補助機能であり、「安全」「すべて隠す」といった表現はしない

試作(ARCH §1.4、2026-10-09)で、OS 標準の文字認識(Vision)は Rust から呼べ、フル HD を 0.16〜0.8 秒で読めること、日本語も読めることを確認した。一方、OS 標準の固有表現抽出(NLTagger)は日本語の人名・会社名・住所を 1 件も判定しなかった。

## 判断

**文字の読み取りは OS 標準の文字認識を Rust から直接呼んで端末内で行い、機密らしい箇所の判定は Rust の規則(書式・手がかり語・行の位置関係)と、承認済みの小さな自作辞書で行う。**

詳細:

| 項目 | 決定 | 根拠・実装 |
| ---- | ---- | ---------- |
| 通信しない | 読み取り・判定・辞書のすべてを端末内に置く。辞書は `include_str!` で埋め込み、実行時に何も取得しない。CSP・権限(`capabilities/`)は変えない | ARCH §12。AM-T25 で差分 0 を確認 |
| 文字を残さない | webview へ返すのは候補の矩形と 4 分類の種類だけ。読み取った文字列は `SensitiveText` で包み(`Debug` は伏せ字・`Display` なし)、`masking/` では出力系のマクロを使わない。パニックフックで文言を出さず発生場所だけを出す | `src-tauri/src/masking/text.rs`、`src-tauri/src/lib.rs` の `install_panic_hook`(AM-T25-F2) |
| Rust で判定する | 読み取りと判定を 1 回の IPC コマンド(`scan_sensitive_text`)の中で終える | 文字列が IPC を通らない構造になる。部分範囲の領域は読み取り結果のオブジェクトが生きている間しか取れない(ARCH §15 #2) |
| 読み取りの呼び出し方 | `objc2-vision`(`default-features = false`、必要な機能だけ)で直接呼ぶ。精度優先・`ja-JP` → `en-US`・言語補正オフ | 新しく増えるクレートは 1 件だけで、補助プロセス・署名・公証の手順が変わらない(ARCH §15 #1 A)。言語補正はオンにすると口座・手がかり語の値の検出率が下がった(`output/reports/masking/eval-2026-10-09.md`) |
| 規則 + 自作辞書 | 書式(メール・電話・URL・トークン・カード・IBAN など)、手がかり語(ラベル・敬称・会社の種類)、行の位置関係(ラベルの右隣・直下・表の列)、自作辞書(日本の姓 767・ローマ字の姓 835・名 408・都道府県 47) | 辞書は `/legal-check`(AM-T01)と `/security-scan`(AM-T20)を通し人間が承認。SHA-256 を同梱時に照合(AM-T21・AM-T25) |
| 判定の方針 | 見逃しを減らす側に倒し、誤検出はある程度許す。候補は利用者が外せる | PRD §1.1 |

## 検討した代替案

### 代替案 A: クラウドの AI(画像を外部の API へ送って判定)

- **メリット**: 人名・住所・未知の書式など、規則では拾えないものにも強い。端末の性能や OS の版に依存しない
- **デメリット**: 機密を含みうる画像を外部へ送る。通信が要り、オフラインでは使えない。API キーの管理・費用・送信先の規約と保存期間の確認が要る
- **不採用理由(却下)**: 「外部との通信なし」「読み取った文字を残さない」(NFR-002)という製品の約束と正面から矛盾する。機密を守るための機能が機密を外へ出すことになる

### 代替案 B: OS 標準の固有表現抽出(NLTagger)で人名・会社名・住所を判定する

- **メリット**: OS 標準で依存が小さい(`objc2-natural-language` 1 件)。端末内で完結する
- **デメリット**: 試作で、日本語の文(人名・住所・会社名を含む)でも全語が `Other` になった。英語も文の中の人名・地名だけで、名前だけの行は言語の判定自体を誤った(ARCH §1.4)
- **不採用理由(却下)**: 対象の大半を占める日本語の画面に効かない。英文の中の人名に限った併用(ARCH §15 #3 C)は、手がかりの無い英字の名前を拾う手段として次の版の候補に残す

### 代替案 C: 端末内の言語モデル(OS 付属のもの、または同梱するもの)で判定する

- **メリット**: 端末内で完結したまま、規則では拾いにくい人名・住所・未知の書式に強くなりうる
- **デメリット**: OS 付属のモデルは新しい OS と対応機種に限られ、対応 OS の下限(macOS 14)を満たさない。同梱するとアプリが大きくなり、モデルの出典・ライセンス・供給経路の確認が要る。処理時間(NFR-001)と、出力の再現性(評価で同じ結果を出せるか)も未確認
- **不採用理由(見送り)**: 今の対応 OS・機種の範囲で全員に同じ機能を出せない。規則ベースの限界(下の「影響」)が確認できたため、**次の版の候補**として、対応環境だけで規則と併用する形を検討する

### 代替案 D: 読み取りを Swift の補助プロセスで行う(ARCH §15 #1 B)

- **メリット**: 読み取りが落ちてもアプリが落ちない。プロセス終了で文字列が確実に消える
- **デメリット**: 補助バイナリの署名・ハードンドランタイム・公証・CI の手順が増える
- **不採用理由**: 試作で直接呼び出しが動き、依存 1 件で済んだため。問題が出たら `RecognizedPage` トレイトの実装の差し替えで移れる(ARCH §16)

### 代替案 E: 判定を TypeScript 側で行う(ARCH §15 #2 B)

- **メリット**: Vitest でテストでき、フロントの開発者が触りやすい
- **デメリット**: 読み取った文字列と全文字の位置を webview へ返す必要がある
- **不採用理由**: 文字列が IPC と webview を通り、NFR-002 を構造で守れない

読み取り方:

- 本番 28 枚では、形が決まっている 9 細分がすべて 95% 以上、固有名詞と手がかり語付きの番号が 70% 以上になった(NFR-003 の目標)
- ホールドアウトでは、**未知の書式・配置で大きく落ちる**ことを 3 回とも確認した。書式を広げると、広げた書式(holdout1・holdout2 の画面)では上がるが、まだ見ていない画面(holdout3)では別の書式・配置で落ちる。これは「見たことのある形だけを拾う」規則ベースの限界で、規則を足し続けても未知の画面での実力は同じようには上がらない
- 形で決まるもの(トークン・長いランダム列・メール)は未知の画面でも比較的保たれる。落ちやすいのは手がかり語の一覧に無い番号、ラベルの無い人名(とくに欧米系)、珍しい書式の金額・口座、住所

### 人間の判断(2026-10-09)

- **書式の拡張は 2 周で打ち切る**(1 周目 `fae37fb`、2 周目 `3680c14`)。未知の画面での伸びが小さく、規則を足すほど誤検出と保守の負担が増えるため
- **得意・苦手を明示して出す**。README・紹介ページに「拾いやすいもの」「見逃しやすいもの」を書き、印は目安であり貼る前に目で確かめる必要があることを示す(NFR-005)
- **人名は目安扱い**にする(AM-T23 で提示した選択肢 3)。ホールドアウトでの人名の検出率が低いため
- 1 字の姓、英字の 2 字の辞書の語(`go`・`ai` など)は、手がかり語なしでは使わない(誤検出を抑える。AM-T20・AM-T22)
- ホールドアウトは規則の調整に使わない。調整に使ったセットは以後「開発用」として扱い、未知の画面の実力は新しいホールドアウトで測る

### ポジティブな影響

- 通信なし・文字を残さないという製品の約束を、構造(IPC の形・型・パニックフック)で守れる
- 依存の追加は `objc2-vision` 1 件だけで、配布・署名・公証の手順は変わらない
- 処理が速い(評価画像 1 枚 約 0.35 秒。実機での中央値・最大値の記録は AM-T24)
- 規則は決定論的で、評価ハーネス(`masking::eval`)で同じ結果を再現できる。どの規則がどの見逃しに効いたかを説明できる

### ネガティブな影響・リスク

- 未知の書式・配置では見逃しが多い(上の表)。利用者が印を信じて確認を省くと漏えいにつながるため、文言で補助機能であることを伝え続ける必要がある
- 規則と手がかり語の一覧が大きくなった(`detect/identifier.rs` だけで約 94KB)。足すたびに誤検出と保守の負担が増える
- ホールドアウトは各 2 画面・8 枚と小さく、数値の幅は大きい
- **既知の制限**:
  - 読み取りに時間の上限が無い(AM-T25 の Low)。上限を付けるには依存の機能の追加が要るため、今回は既知の制限とした
  - macOS 14 と、より遅い機種での読み取り・処理時間は未確認(AM-T24 の手動確認で行う)
  - 2 行目以降の住所(建物名など)・手がかりの無い英字の名前・画面に手がかりの無い番号は、規則では拾えない
  - メモリの消去(`zeroize`)はしない。文字列の複製は OS の内部にもあり、Rust 側だけ上書きしても保証にならないため(ARCH §12)。参照を残さないことで「保持しない」を満たす
